## Mandated requirement vs our implementation (SSM approved by the instructor)
- **M:** the assignment text describes deployment to the server "over SSH".
- **R:** the implementation deploys through **AWS Systems Manager (SSM)** and **CodeBuild**, authenticated with **GitHub OIDC**. No SSH is used and no inbound port 22 exists.
- **SSM instead of the SSH wording is approved by the instructor (stated by the owner on 2026-11-23; no written confirmation is stored in this repository).** This approves the method only: AWS IAM permissions, infrastructure access and budget are separate and are NOT available or approved, and nothing is deployed.
  The reasoning for choosing SSM (no open port, no stored key) is in `AWS_STAGING_INTEGRATION.md`.

## Tiers
| Tier | Technology | Role |
|---|---|---|
| Presentation | React + Vite build, static files served by a pinned Nginx container | Public UI (M) |

## Topology (staging, ap-south-1; written in Terraform, not created)
```
 Internet ─ HTTP 80 (allow-listed CIDRs) ─► ALB (public subnets)
                                              └─► EC2 (private app subnet, no public address, no inbound SSH)
                                                    Docker: Nginx ─┬─ /     static frontend
                                                                   └─ /api  backend-blue | backend-green
                                                    └─► RDS PostgreSQL (private db subnet, no internet route)

 GitHub Actions ─ OIDC (short-lived credentials) ─► AWS
                    ├─► ECR            backend image, pushed by immutable tag; the digest is read back
                    ├─► CodeBuild      database migrations, run inside that same image (private app subnets)
                    ├─► S3             release bundle (scripts, settings, frontend build)
                    └─► Systems Manager  fixed command documents (deploy, rollback) sent to the one instance
```

## Component responsibilities
| Component | Responsibility (from `infra/terraform/` and the workflows) |
|---|---|
| **VPC / subnets / NAT** | Public subnets hold the ALB and the NAT Gateway. Private application subnets hold the EC2 instance and the CodeBuild network interfaces. Private database subnets have no internet route. Staging uses one NAT Gateway (a cost choice and a single point of failure). |
| **ALB** | Internet-facing entry point, forwards to Nginx on the instance. Staging is HTTP only (no domain or certificate); the ALB security group accepts only the CIDRs set in an untracked variable file. |
| **EC2** | Runs Docker: Nginx plus the blue and green backend containers. Private, IMDSv2 required, managed only through Systems Manager. Staging has one instance; production is designed for two (not implemented). |
| **RDS** | PostgreSQL, private, encrypted, TLS enforced. The master password is generated by RDS and held in Secrets Manager. Staging is single-AZ; production is designed Multi-AZ with deletion protection. |
| **ECR** | One backend repository (`shopnest/<env>/backend`), immutable tags, scan on push. There is no frontend image: the frontend is built by CI and shipped as static files. |
| **S3** | Private, encrypted, versioned artifact bucket holding release bundles under `deploy/<env>/<sha>/bundle.tar.gz`. The deploy role has PutObject only; the instance role reads `deploy/*`. |
| **CodeBuild** | `migrator` applies migrations from inside the release image; `bootstrap` creates the database roles once. Both run in the application subnets with their own security groups and roles. Only exists when `enable_cicd` is true. |
| **Systems Manager** | Two command documents (deploy, rollback) with fixed commands and validated parameters. The only way the pipeline changes the instance. |
| **IAM** | Five identities: instance role, GitHub deploy role (OIDC), migrator role, bootstrap role, operator role (MFA). Details: `AWS_STAGING_INTEGRATION.md` section 3. |

## Network security
- Security groups: ALB inbound 80 from allow-listed CIDRs only; the instance accepts traffic only from the ALB; the database accepts 5432 only from the instance and the CodeBuild groups.
- **There is no inbound SSH rule anywhere.** Port 22 is never opened, so there is no temporary rule, deploy key or known-hosts secret.
- The instance has no public address. Outbound access (SSM, ECR, Secrets Manager, CloudWatch Logs) goes through the NAT Gateway.
- Validation (pending, needs AWS): an external connection attempt to 5432 must fail; a screenshot of the security groups is the evidence.

## Pipelines
- `ci.yml`: on push and pull request to `main`. Frontend and backend jobs in parallel (install, lint, test, build) on a Node.js 22 and 24 matrix; build outputs are uploaded as artifacts and consumed by CD.
- `cd.yml`: runs after CI succeeds for a push to `main`, only when the repository variable `CD_ENABLED` is `true`. Jobs: `gate`, `package`, `deploy-staging` (Environment `staging`), and `production-approval`, a gate bound to the `production` Environment so that GitHub can hold it for a required reviewer. **Production is not deployed**: the gate has no AWS access and deploys nothing. Whether the approval works is not verified until the Environment is configured and tested in GitHub.
  Every run so far was `skipped`; the deploy jobs have never run.
- `rollback.yml`: manual (`workflow_dispatch`) with an environment and a full commit SHA. Only staging is implemented; a production request, a ref other than `main`, or `CD_ENABLED` not set is refused.
- `terraform-ci.yml`: `fmt`, `validate` and static IAM checks. It is not an AWS acceptance test.
- Workflow permissions are explicit and minimal; third-party actions are pinned to a commit SHA.

## Deployment and rollback (written, never run on AWS)
1. Package: build the backend image and one release bundle for the exact commit.
2. Push the image to ECR and read back its digest; the instance later pulls **by digest**.
3. Run the migrations in the CodeBuild migrator. If they fail, nothing is deployed. The schema is never reversed automatically.
4. Upload the bundle to S3, then send the deploy document through Systems Manager. The instance verifies the bundle's SHA-256, pulls the image by digest and proves the metadata-service isolation.
5. Blue/green: start the idle colour, require `/health` OK and `/version` equal to the commit SHA, then switch Nginx and reload.
6. If validation fails, traffic stays on the old colour and the new colour is stopped (automatic recovery). Exit codes: 0 deployed; 1 failed, previous release serving; 3 failed and recovery failed; 4 result unconfirmed.
7. Manual rollback (`rollback.yml`) re-deploys a release that is recorded as deployed, through the same validation path. It never runs migrations.
- Traceability: the SHA appears in the image tag, a container label, `/version` and the deploy log. Deployment logs are uploaded as workflow artifacts.
- Trade-offs: about twice the backend memory during a deploy; migrations must be backward compatible.
- **Not proven:** a deployment on AWS, zero downtime on AWS, and a real automatic or manual rollback on AWS. A local Docker rehearsal exists (`docs/evidence/bluegreen-local/`) from before the AWS-mode changes; one post-switch fault cost 79 of 171 requests there.

## Secrets and configuration
- **There are no GitHub secrets in the current design.** The workflows read non-secret variables from the `staging` GitHub Environment (names and purposes: `docs/GITHUB_SETUP.md` and `AWS_STAGING_INTEGRATION.md` section 4).
- Database credentials live in Secrets Manager and are read at run time by the roles that need them; the repository holds only names.
- Local AWS access uses the profile `devops` only; no permanent AWS access key is created or stored in GitHub.
- Terraform state and the variable files with real values are git-ignored.
